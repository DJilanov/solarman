# Bluesun controller and commissioning

The supported profile is the Bluesun **BSE20KH3**, 20 kW, protocol 2.02, main DSP 1.57 / HMI 1.45, diagnosed through manually supplied SOLARMAN Customized Command replies. A write acknowledgment alone does not confirm a setting; every software write is read back.

## Required settings

| Holding register | Required value |
|---|---|
| 206–207 | 32-bit flags 0x00000009 normally; 0x00000019 during timed AC charging |
| 2500 | SelfUse, raw 0 |
| 2504 | AC charging ratio raw 100, 10% of 20 kW (approximately 2 kW) |
| 2505 | AC target raw 500, 50% |
| 3005 | Overall maximum SOC raw 1000, 100% |
| 3036 | On-grid reserve raw 500, 50% |

Monitoring can display plausible native readings with different control settings, but hardware controls remain blocked. The controller never silently corrects these settings. It never writes the global SOC target, current limit, BMS protections or off-grid reserve.

Solar charging follows native inverter and battery/BMS limits, with the verified 100% overall SOC target. The owner withdrew the application solar-power-cap requirement on October 29. No solar power-limit register is written. The 2 kW AC setting remains required; exact source attribution during mixed PV/grid charging needs suitable measurements.

The [firmware evidence review](firmware-evidence.md) records the public tables and saved numeric observations. The commissioning page offers an EN/BG diagnostic report before a run exists. Explicit verification retains raw words from reads already performed; exporting the report adds no device request and grants no control permission.

## Firmware verification

Control verification includes protocol 2.02, main DSP 1.57 and HMI 1.45, alongside the eight existing rating/settings/clock checks. The firmware identity is saved with the report and shown with its observation time. Missing or unvalidated DSP/HMI versions permit monitoring but cannot pass control verification. Unknown model/protocol mappings retain raw provider monitoring only.

A fresh online upload reporting a different model/protocol/firmware, or a legacy successful report without a firmware identity, revokes workspace activation atomically, persists pause, cancels manual intent and advances cancellation epochs. Existing scheduled permission remains an obligation of its original device and is cleared through the existing recovery path where permitted. Failed cleanup remains pending and does not rearm control after restart. A start interrupted by this observation is recorded as interrupted with its firmware event. Cached, stale or offline reports cannot establish a firmware change. Verification and later workspace activation are separate steps; returning to a known firmware does not automatically reactivate control. These checks use the existing provider read and add no monitoring requests.

The product action is **Stop scheduled top-ups**: it pauses application requests and clears scheduled AC permission. It cannot promise that native reserve charging stops below 50%. Solar charging, the global 100% SOC target and native reserve settings are not changed by this action.

The [manufacturer model datasheet](https://www.bluesunpv.com/wp-content/uploads/2024/12/BSE20-30KH3_v2406-Rev-01_EN.pdf) describes electrical ratings. The application leaves solar power limits to the native inverter and battery. The generic maximum-charging-power entry and the installation's observed raw 100 remain diagnostic information; no power-limit write was added.

## Runtime behavior

Monitoring uses one provider telemetry request every five minutes for a single workspace, projecting to 105,120 regular requests/year. Native diagnostics read flags, AC configuration, battery registers 2000–2008, flow registers 507–554 and policy registers 3005–3036. Steady active supervision adds these five native reads at the first poll after an hourly audit becomes due, projecting to 148,920 regular requests/year in total. Starts, due top-up assessments, observed deviations and existing owned schedules trigger earlier native checks.

A standard Modbus read (function 3 or 4) retries once, after one second, when its correlated provider callback reports delivery error 530. Each attempt has a separate callback URL and repeats request pacing, quota reservation and dispatch authorization with the original routine/recovery purpose. Failed order-ID correlation, invalid read frames, other device errors, HTTP/submission failures and unknown outcomes do not trigger this retry. Writes are never replayed by this mechanism. Shutdown prevents a pending retry from dispatching; snapshot and attended-session deadlines continue to apply. Additional attempts consume the existing request allowance, including its transition margin, and remain subject to the actual quota guard. The steady polling projections and cadence are unchanged.

Shared admission reserves each enabled workspace's largest periodic workload, even when paused: either six requests per scheduled charging cycle, or telemetry plus five native reads per assessment/audit interval. A monitoring-only workspace reserves telemetry alone. Allocation retains a 5% margin for authentication, manual checks and transitions, plus the separate recovery reserve. With the default 200,000-call allowance and one control workspace, telemetry remains five minutes, scheduled checks use 17 minutes and below-reserve assessment eligibility uses 32 minutes. This reserves 187,245 of 188,000 planned regular requests/year. Repeated cached uploads and manual diagnostics cannot postpone an already due automatic assessment. Scheduled cadence never exceeds the configured window minus more than three minutes.

Admission and activation take the App ID's PostgreSQL row lock, so concurrent workspaces cannot reserve the same final capacity. Pause retains control capacity; **Disable workspace control** revokes activation and releases it while preserving any cleanup obligation. A capacity-waiting workspace retries admission without device polling, retains credential/discovery access and can still perform manual diagnostics or recovery. If saved activation no longer fits at startup, pause and cancellation persist before normal work; cleanup survives revocation. The UI distinguishes current-mode projection, reserved workload and prospective activation. PostgreSQL request reservations still enforce actual usage before HTTP dispatch; routine requests cannot consume the default 2,000-call recovery reserve. Stop, cleanup authentication and readback use recovery capacity. A quota or active native-check failure pauses active intent and attempts cleanup, with retries only while cleanup remains unconfirmed.

When scheduled AC permission is off and native battery charging is already at least 1.8 kW, the service leaves it unchanged. Solar surplus of at least 1.8 kW also prevents a new timed top-up; 2 kW stops an existing one. When a grid top-up is still needed, fresh native settings, grid voltage and battery state must permit it before the service requests and verifies a bounded daily charging window (normally 25 minutes). The native 50% AC target stops charging independently of the scheduler poll. AC permission is removed at or above 50%, restoring normal battery use above the reserve. Short windows are renewed only while needed. The five-minute telemetry path never enables a write by itself.

Two distinct newer uploads establish an observed deviation: at least 52% SOC, house/solar deficit above 250 W, grid import above 250 W and battery discharge below 100 W; or 50–98% SOC, solar surplus above 500 W and battery charging below 100 W. A newly observed deviation triggers one early native check, then the ordinary audit interval applies until the episode changes. These are diagnostic notices about expected behavior, not exact source-attribution claims or BMS overrides. A native settings failure pauses control; a temporary grid/battery-not-ready decision retains an outstanding manual request until its usual completion, cancellation or expiry.

These windows are **daily schedules, not an expiring watchdog**. Process failure, a network outage or an unreachable API can prevent cleanup; the last window may repeat on later days until AC charging is disabled. The midnight minute is excluded; a window crossing midnight uses two intervals. The inverter clock/timezone must match the linked account. Native inverter and BMS protections remain responsible for battery safety.

On errors and graceful shutdown, live mode attempts to remove timed AC permission while preserving all other flags. An API outage can prevent confirmation. Paused monitoring retries an unconfirmed stop before fetching telemetry; starting remains blocked until cleanup succeeds. An armed runtime also reconciles scheduled permission once after restarting. Ambiguous submissions are not automatically retried as though nothing happened.

## Durable recovery

`device_control_state` retains ownership of possible scheduled permission for each tenant/account/inverter binding. `inverter_write_intents` stores the requested register values and originating command job before dispatch, followed by separate acknowledgment and readback timestamps. The write guard checks the current database activation, pause intent and discovered device immediately before preparing a change. A stop arriving during an in-flight write keeps cleanup pending even when that write's late readback succeeds. Unknown outcomes are retained until reconciliation and are never relabeled as verified original writes.

Pausing or changing account access advances `controller_state.control_epoch` in the same transaction as the persisted pause. Starts capture that generation when accepted and apply their state changes only if it still matches. This prevents a start whose database update was delayed from overwriting a newer stop, including after a process restart. Repeated cleanup preserves the pause without continually invalidating later requests.

Failed control checks are also retained in `device_health`. A stored fault forces paused intent and cancellation of outstanding starts after a restart, even if the older controller row still requested active control. Normal provider telemetry does not clear this fault. Fresh native diagnostics must succeed before normal starts become available again. System health records persistent recovery and quota alerts; marking one as seen has no effect on control permission or the inverter.

On restart, owned permission becomes cleanup-required before evaluation. A successful off read/modify/write and readback, or a fresh diagnostic flags read showing permission off, confirms its observed state and resolves the cleanup obligation. The original uncertain write remains marked uncertain, with a separate reconciliation timestamp. This is a point-in-time observation, not proof that a delayed vendor command can never arrive later; interruption and late-command behavior still require physical commissioning.

Credential repair preserves the original cleanup target while pausing and revoking normal control. Once discovery with the new credentials confirms ownership of that same inverter, recovery can remove scheduled permission under the existing host permission without rearming the workspace. Normal starts remain disabled until fresh verification and activation. Changing the selected inverter, compatibility profile or timezone cannot abandon an unresolved binding. Host write permission, valid account access and the recovery API budget remain necessary for physical changes.

Controls displays the five latest write records with intent, acknowledgment, readback and reconciliation times, linking each originating command to its Activity detail page. Activity shows the recorded request, device, actor, decision, verification and all associated write intents in pages of 25. Its **All inverter writes** view includes the complete workspace journal across old bindings and system recovery writes without a command ID. Requested values, acknowledgment, readback and reconciliation remain distinct; cleanup never changes the original uncertain write into a verified one. New jobs capture the device at acceptance, while older jobs without reliable write or device-verification evidence show an unrecorded device. Reading history never dispatches a device request.

## Commissioning

Controls separates the saved device verification from the current clock evidence. A failed saved clock check can coexist with a newer passing observation; only an explicit successful full verification renews the report for activation. The UI shows the report state and activation deadline, actual clock comparison timestamps and tolerance, firmware identity, responsible actor and next action for every blocker. The clock timestamp remains the device upload time on repeated cached responses. Future clock evidence beyond the provider's 30-second allowance, invalid timestamps and expired evidence cannot satisfy the current-clock gate. Activated workspaces continue through native supervision without requiring reactivation every 30 minutes. Command notification failures preserve an unconfirmed outcome and link to the known command, or to Activity history when acceptance itself was not confirmed.

1. Obtain App ID / App Secret and custom-command permission, with a licence appropriate for hosted users.
2. Verify the public HTTPS callback reaches the correct linked account. Callbacks correlate the random command URL, device, original request, timestamps, optional order ID and Modbus CRC/function/count.
3. Test account discovery and bind the actual inverter to the correct workspace and timezone.
4. Keep `WRITES_ENABLED=false`; use Refresh readings and confirm signs, values and the combined register ranges on the actual firmware.
5. In Controls, run **Verify device settings** while automation is paused. This reads input 7–8, the existing diagnostics and provider metadata, checks 20,000 W rating, six policy settings, the reported inverter clock and firmware identity, and persists nine results. The clock must match the workspace timezone within two minutes of the logger collection time. This operation never enables writes. A failed verification invalidates the previous report before device requests begin.
6. Open **Commission the home policy** and prepare a device-bound run after fresh verification. Preparation works with host writes disabled and does not change the inverter. Collect policy observations separately and save their snapshot in commissioning.
7. For an attended physical test, the server operator permits hardware writes. After fresh verification, confirm attendance with the current dashboard password and open a 30-minute session. **Enable attended controls** reserves control capacity while normal automation stays paused; **Test grid top-up to 50%** is the explicit test action. Ordinary Resume and top-up remain blocked without approved commissioning. Stop remains available during pending work.
   When SOC is at least 52%, **Test scheduled-permission recovery** offers a separate attended check. Confirm its disclosure, then request the test. It freshly checks the supported settings, grid and battery, enables only the scheduled-permission flag and verifies it, then uses normal Stop cleanup and a final flags read. It preserves the original charging windows, SOC targets and power settings. The temporary request always returns to paused intent; cleanup failure stays visible and requires recovery. Stop remains available throughout. This checks permission recovery separately from real grid charging and stopping at 50%.
8. Ending or expiring the session persists pause, cancels manual intent, revokes activation and retains/attempts physical cleanup. Expiry is checked every 15 seconds without provider requests; every enabling dispatch independently rechecks its deadline. Restart cancels all attended sessions before loading runtimes. Application expiry does not turn daily inverter schedules into a physical watchdog; failed cleanup remains visible and recoverable.
9. Review the checklist's available observations, then save them with the current dashboard password. Optionally choose a verified recovery result by action/time from the latest 20 eligible commands and review its Activity details. Only successful commands from this commissioning run with a verified disable write on the same inverter qualify; observing permission already off is insufficient. A named recovery test additionally requires a verified enable from the same command before its disable write. Failed or interrupted tests do not qualify, including when later cleanup observes permission off. Saved and newly available evidence remain distinct. Unattended approval requires all four observed charging/discharging signals, full day/night coverage and verified recovery. Solar power uses native inverter and battery limits. Approval, workspace activation and Resume remain separate actions.

Real OpenAPI discovery, HTTPS callbacks, combined diagnostic register reads and the 20 kW rated-power register have been verified. Physical write commissioning remains outstanding. Reported clock comparison is now part of preflight and monitoring. Recorded production measurements show battery charging while timed AC permission is off: this flag is not proof that every native grid charging mechanism has stopped.

Observed native behavior on 2026-10-28: at 10:15 UTC, SOC was 48% and battery charging was 1,947 W with scheduled AC permission off. At 10:31 and 10:34 UTC, SOC was 50% and battery power was 0 W, with house demand supplied by solar and grid. No application writes were enabled. This supports native reserve charging and stopping at 50% for those observations; it does not yet establish solar charging or house supply from the battery above 50%.

The later October 29 observations show approximately 1.93 kW charging at 49%, then two consecutive stopped readings at 50% with no solar generation. The observation detector starts its stop candidate only near a charging approach; subsequent qualifying readings use the existing continuity check, allowing ordinary upload drift. Gaps or conflicting readings reset unfinished candidates. Historical progress is not automatically recalculated when detector code changes. See [finish-plan.md](finish-plan.md) for the exact timestamps and read-only replay scope; these signals do not approve unattended control.

Workspace control is stored separately from the host permission in `controller_state.control_enabled`; new workspaces default to disabled. Device verification is bound to the selected serial number and profile. Credential updates and inverter selection revoke the old verification and activation. Stop/Pause records its intent before waiting for device work, cancels older queued starts and allows cleanup even after a settings verification error. The six-hour expiry of a manual request bounds application intent, not the daily schedule stored inside an unreachable inverter.

Workspace suspension uses the same persisted cancellation and cleanup mechanism, revokes activation and verification, and releases normal control capacity. Monitoring and recovery remain available. Starts are checked again after provider pacing/quota reservation, immediately before dispatch; an already dispatched command can still arrive later and must be reconciled. Making a workspace available does not resume automation or clear an unresolved cleanup obligation. Administrator availability changes require the current dashboard password and the displayed lifecycle revision.

## Manual recovery

Pause the workspace or stop its controller before changing the same flags manually. **Do not run two controllers for one inverter.** If the API is unavailable, this previously tested Customized Command disables AC charging with the known run/EPS flags:

```text
011000CE00020400000009BE75
```

Read flags with `010300CE0002A5F4`; the known disabled reply is `010304000000093A35`. The software normally performs a fresh read/modify/write so unrelated flag bits are preserved; the exact manual command above assumes the diagnosed flags.

The legacy single-device CLI remains available through `npm run inspect`, `npm run start:worker` and `npm run disable`, using the provider environment variables. It is separate from tenant scheduling and must not run alongside this dashboard against the same device. `inspect` never writes, even when the environment enables writes.
