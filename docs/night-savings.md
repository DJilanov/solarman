# Forecast and tariff planning

This feature adds per-workspace installation/tariff settings, frozen hourly solar forecasts, household demand prediction, a costed battery plan, forecast-versus-actual feedback, suggested solar-surplus load times and estimated backup endurance. A clear mode/next-action summary links Home, Automations and the planner. English and Bulgarian share the existing glass electronics interface.

## Completion requirements

1. Site settings support multiple roof planes, registered provider-location hints, battery energy/power/efficiency/reserve assumptions, prices/currency/export value and calendar-based seasonal tariff windows. Missing or assumed inputs remain visible. Settings, history and actions are tenant-bound and revision checked.
2. Forecasts come from a real provider through bounded, cached, validated requests. The forecast timestamp, source, assumptions, range and freshness are displayed. Hosted-commercial use supports the provider's licensed endpoint; evaluation use is explicit. API keys remain server-side. Forecast errors never become zero solar.
3. A chronological energy/cost simulation includes current SOC, overnight and daytime load, PV, charge/discharge limits, losses, protected reserve, export value, optional cycling cost, feasible charging duration and solar headroom. The selected target is compared with a normal-policy baseline; a more expensive night tariff must not encourage night charging. Gaps and sparse history affect quality rather than becoming zero consumption.
4. Recommendations include explanatory reasons and a 15-minute timeline through the next charging opportunity. Use tonight freezes an explicit plan; Automatic is an opt-in persisted policy. Both recheck current readings, settings, forecast, device binding, permissions, quota and competing control ownership before dispatch.
5. Night savings holds/top-ups only in the configured tariff window and returns to the verified normal policy for daytime battery use. Existing outage reserve has priority and is never expired by the weather planner. Native windows bound grid charging; delayed/unconfirmed restoration remains durable and visible. Unknown writes are never blindly repeated. Pause, stop, restart, account changes, suspension, restore, rollback and erasure retain recovery obligations and cannot silently re-arm automation.
6. Saved forecasts are scored against subsequently observed data using actual coverage. Calibration excludes possibly curtailed/limited days. Financial benefits remain estimated counterfactuals, with loss/wear assumptions and missing periods disclosed. No saved forecast is replaced by hindsight.
7. Backup endurance uses configured battery capacity, a protected discharge floor and either stated essential load or explicitly labelled recent household demand. Surplus-load suggestions remain recommendations unless actual device control is separately connected.
8. Unit, PostgreSQL integration and browser tests cover the algorithm, seasonal tariffs/DST, input boundaries, gaps, economics, tenant isolation, security, idempotency, modes, execution/recovery and EN/BG mobile states. Schema releases include matching recovery-tool installation, older/fresh checkpoint drills, immutable PM2 deployment, live read-only verification and unchanged hardware until the owner explicitly activates a plan.

## Tariff time

The Bulgarian household template follows the supplier's published calendar periods: April–October 23:00–07:00 and November–March 22:00–06:00. These changes occur on fixed calendar dates, independently of daylight-saving clock changes. Instants and durations use UTC; pricing uses the site's IANA local time. A configured contract can use other periods. Source: https://electrohold.bg/bg/sales/domakinstva/snabdyavane-po-regulirani-ceni/ . Prices are supplied/confirmed by the account owner, not inferred from the template.

## Forecast source

Open-Meteo provides hourly global tilted irradiance, temperature and cloud cover. Radiation values are preceding-hour means; conversion must preserve that interval alignment. Model estimates use each plane's kWp, tilt and azimuth, declared system/temperature losses and the inverter ceiling. Initial uncertainty is an assumption until frozen forecasts can be calibrated against sufficient unconstrained observations. Provider access/attribution follows https://open-meteo.com/en/docs and https://open-meteo.com/en/pricing .

## Using the planner

Open `/controls/night-savings`, enter the installation and tariff settings, then refresh the recommendation. A 15-minute model compares the normal reserve policy with feasible night targets. Adjust recalculates an explicit target without changing the inverter. Use tonight saves a one-time plan; Automatic authorizes future nightly recommendations within the configured maximum, including nights when no extra charging is initially suggested. Both require the current dashboard password and the existing verified control permissions. Automatic is initially off.

The scheduler recalculates at the cheap period's start with fresh readings and a current forecast. An unadjusted one-time recommendation may decrease, and never increases without review; an explicitly adjusted target is preserved for that night. Subsequent automatic nights use the installation's configured maximum. Unreachable targets, stale readings, changed permissions, missing forecasts or competing controls prevent a new application. The approved inputs remain in `approved_snapshot`; the execution inputs are saved separately on the plan. Native apply/restore writes retain the existing per-write journal, dispatch authorization and readback checks.

Night savings uses the supported profile's 50% operating reserve and 2 kW AC charging limit. Model inputs for PV charging, discharge power, efficiency and backup load are planning assumptions until confirmed; entering them does not program physical battery limits. Solar charging retains the native 100% ceiling and BMS limits. Outage reserve takes priority, with a durable queued transition that restores the night settings before applying the explicitly requested outage target. An expired night plan cannot cancel an outage reserve.

Native time windows are daily schedules. If the service or provider remains unreachable, grid charging can repeat in a later matching window and Maintain mode can continue to hold energy instead of resuming daytime discharge. A separate deadline loop starts normal restoration five minutes before the cheap period ends; the request stays pending until verified. Recovery faults feed the existing operational incident/notification channel. No cloud-only plan can make a daily native window expire while the inverter is unreachable.

## Forecast access and estimates

`ENERGY_WEATHER_MODE=disabled` is the default. For a single personal prototype, set `evaluation` and `ENERGY_WEATHER_EVALUATION_TENANT` to that workspace UUID. Other workspaces remain without forecast access. Hosted commercial use requires `commercial` and the operator's `OPEN_METEO_API_KEY`; subscription purchase is a separate operator decision. Keys stay server-side. Weather requests are bounded, serialized and cached for three hours. New site geometry or changed calibration/uncertainty assumptions require a matching forecast rather than reusing a mismatched model.

The initial solar range is a configured scenario margin, not a probability interval. Calibration requires seven distinct completed days, at least 95% measured coverage and no suspected curtailment. Only forecasts frozen before the local day starts qualify. Sparse household history uses observed hour patterns, then an explicit daily estimate or an observed average, with additional demand margin. Missing readings and weather values never become zero production or consumption.

The installed BSE20KH3 stayed idle after a 53% hold with the 50% reserve, but resumed house supply after a 56% charge and continued discharging at 54%. Model v2 therefore uses a conservative six-percentage-point restart band. This is a planning bound, not a confirmed exact firmware cut-in setting. A current discharge reading preserves the running state below that bound; reaching reserve or entering a hold resets it. Solar or grid charging can raise SOC enough to restart it. This prevents forecasting immediate usable discharge from a small top-up near reserve. Native reserve/charge/protection settings are not programmed by this model. The PV-site identity remains at its original version so yesterday's frozen solar forecasts remain available for scoring.

Costs use the owner's configured all-in prices. Export payment defaults to zero; an unspecified cycling allowance excludes wear and is disclosed. Historical comparisons match the observed periods and include configured cycling cost. They show actual coverage and estimated counterfactuals, not verified bill savings. Interrupted and uncompleted plans do not receive an outcome saving estimate. Backup endurance is an energy estimate based on the protected floor and a declared essential load or recent household consumption; it does not certify EPS wiring, peak capability or actual outage operation. Flexible-load suggestions do not switch appliances.

## Operations and data lifecycle

Schema `024_energy_planning.sql` adds workspace settings, frozen forecasts, plans, outcomes and action receipts, plus the night purpose/deadline on the existing native reserve journal. No additional production dependency is needed. Calculation workers keep CPU-heavy simulations off the HTTP/scheduler thread. Settings and actions use tenant ownership, CSRF, revisions, current-password confirmation for activation and idempotent receipts. Account/firmware/commissioning changes, suspension, rollback and database restoration revoke automatic approval. Restart retains pending native restoration and never replays an uncertain apply.

API capacity reserves 64 additional calls per control workspace per day for a complete night apply/restore cycle, alongside normal monitoring/assessment and the recovery reserve. The shared command queue admits at most three night plans with restoration deadlines within three minutes of one another. Further requests remain blocked with a capacity reason; they are not silently run late. This is an operating limit of the current single-server dispatcher.

Workspace archives include energy settings, forecasts, approved/executed plans and outcomes. Retention removes expired outcomes, inactive plans and unreferenced forecasts while preserving native recovery evidence. Minimal action receipts remain until workspace erasure to prevent replay. Erasure deletes native evidence before referenced plans and forecasts. The recovery capsule must be installed before deployment; older and fresh checkpoint drills verify schema upgrade and quarantine active night plans/automatic approval without device access. A release lacking schema 024 cannot be used for rollback after upgrade.
